# AI 聊天智能体小程序 PRD（MVP）

> 返回：[文档基线](../README.md) · [技术架构](../architecture/technical-architecture.md)

> 版本：1.0
> 更新日期：2026-11-07
> 目标平台：微信小程序优先，H5/App 只保证可编译
> 产品形态：借鉴微信“会话列表 + 单聊页”的熟悉信息结构，不复制微信品牌、名称或视觉资产

## 1. 产品定位

做一款低学习成本、以文字对话为核心的个人 AI 智能体。用户打开即进入会话，使用接近微信聊天的交互提问、追问、停止生成和查看历史；后端通过 FastAPI 统一接入一个或多个大模型服务。

核心价值不是堆叠工具入口，而是让用户在最少操作下完成一次有效问答，并可持续追问。

### 1.1 MVP 目标

- 新用户完成微信授权后，30 秒内得到第一条 AI 回复。
- 支持连续多轮文字对话、历史会话恢复和异常后重试。
- 客户端不保存、不接触任何模型 API Key。
- 主包不超过 2 MB，首屏和输入链路适配中低端安卓机。
- 形成可上线验收的登录、对话、隐私、内容安全和基础运维闭环。

### 1.2 非目标

- MVP 不实现购物平台账号密码登录、订单抓取、网页爬虫或第三方平台凭据代管。
- MVP 不实现语音通话、实时语音、多人会话、复杂 Agent 编排、知识库 RAG 和支付订阅。
- MVP 不提供模型参数面板；普通用户只看到“智能助手”，高级模型切换后置。
- 不追求 H5/App 功能完全一致，不为多端一致牺牲微信小程序体验。

## 2. 用户与场景

### 2.1 目标用户

- 需要快速获得答案、写作辅助、信息整理和日常决策建议的个人用户。
- 已习惯微信聊天交互，不希望学习复杂 AI 产品界面的用户。
- 对隐私、历史和响应稳定性敏感，但不要求专业提示词工程能力的用户。

### 2.2 高频任务

- 提问和连续追问。
- 摘要、改写、翻译、头脑风暴。
- 将一段长文本整理成结构化内容。
- 回看、继续或删除历史对话。

### 2.3 核心用户旅程

1. 首次打开小程序，阅读隐私说明并主动授权。
2. `wx.login` 换取临时 code，FastAPI 调用微信接口建立本站会话。
3. 进入“对话”页；点击“新对话”或继续已有会话。
4. 在底部输入框发送文字，立即看到用户消息和 AI 等待状态。
5. AI 回复逐段出现；用户可停止生成、复制内容或在失败后重试。
6. 返回列表后可继续历史会话；也可删除会话和退出登录。

## 4. 信息架构

MVP 使用两个底部 tab：

- **对话**：会话列表、新建会话、进入聊天。
- **我的**：基础资料、清除历史、隐私协议、关于、退出登录。

低学习成本优先于功能密度，不设置“购物、工具、知识、我的”四宫格入口。工具和知识后续优先成为聊天内能力，而不是独立首页模块。

### 4.1 页面清单

| 页面 | 路由建议 | 核心内容 |
| --- | --- | --- |
| 登录/隐私页 | `pages/login/index` | 隐私同意、微信登录、失败重试 |
| 会话列表 | `pages/chat/list` | 新对话、最近会话、删除、空态 |
| 聊天页 | `pages/chat/detail` | 消息流、输入框、停止、重试 |
| 我的 | `pages/me/me` | 资料、历史管理、协议、退出 |
| 设置 | `pages/me/settings` | 模型说明、清缓存、版本号 |

聊天主链路放在主包；关于、协议、设置等低频页后续可迁入分包。

## 5. 交互与视觉原则

### 5.1 会话列表

- 页面顶部展示标题和“新对话”入口。
- 每条会话展示标题、最后一条消息摘要、相对时间；标题默认由首轮问题生成，失败时截取用户首条消息。
- 支持下拉刷新、触底分页、左滑删除，删除需二次确认。
- 空态直接提供 3 个轻量示例问题，点击后创建会话并预填，不自动发送。
- 弱网时优先展示本地缓存列表，并明确标记“历史可能未同步”。

### 5.2 聊天页

- 自定义导航栏：返回、当前会话标题、更多菜单。
- 用户消息右对齐，AI 消息左对齐；不复制微信具体配色和品牌元素。
- MVP 的 AI 内容按纯文本展示，保留换行；Markdown 必须经过安全白名单渲染后才可上线。
- 底部输入区固定并处理安全区，使用多行输入框，1 至 4 行自适应。
- 输入为空不可发送；每会话同一时间只允许一个生成任务。
- 生成中发送按钮切换为“停止”；停止后保留已生成内容并标记“已停止”。
- 用户停留在底部时自动跟随新内容；用户主动上滑阅读后不强制拉回，只显示“回到最新”。

### 5.3 消息操作

- 用户消息：复制、失败重发。
- AI 消息：复制、重新生成、失败重试。
- 长按操作优先，避免气泡内常驻过多按钮。
- 删除会话和清空历史属于破坏性操作，必须二次确认。

## 6. 功能需求

### FR-01 登录与会话恢复

- 首次登录前展示隐私政策和用户协议，用户拒绝时提供只读说明页，不进入对话。
- 使用 `Taro.login()` 获得 code，并调用 FastAPI `POST /api/v1/auth/wx-login`。
- 客户端只提交 `{ code }` 字符串，不得直接把 `Taro.login()` 的整个结果对象传给接口。
- 后端使用 code 换取 `openid`，签发本站 access token 和 refresh token。
- 冷启动先恢复登录态；access token 失效时尝试刷新，刷新失败后清理状态并跳转登录页。
- 不强制获取头像昵称；用户主动选择头像昵称时才保存。

### FR-02 会话管理

- 新建会话后立即进入聊天页，创建失败时保留输入并显示重试。
- 列表使用游标分页，不依赖页码。
- 会话标题支持自动生成和手动重命名。
- 删除采用软删除；服务端至少保留 7 天用于误删恢复，再异步物理清理。
- 同一用户的 `client_message_id` 在单个会话内必须幂等，重试不能产生重复消息。

### FR-03 文本对话

- MVP 只接受文本，单条建议限制 2,000 字，服务端必须再次校验。
- 用户发送后 100 ms 内完成本地乐观插入，不等待服务端响应。
- 服务端将用户消息持久化后创建生成任务，返回消息 ID 和 run ID。
- 回复优先流式输出；流式失败时保留已生成内容，并允许重试。
- 上下文采用“系统提示词 + 最近消息窗口”策略；P0 以 token 预算截断，P1 再加入长会话摘要。
- 服务端为每次生成设置总超时和最大输出 token，避免无限占用并发。

### FR-04 异常与恢复

- 断网、超时、限流、模型不可用、内容拦截分别使用可理解的提示，不直接展示供应商原始错误。
- 重试分为“重发用户消息”和“基于已有用户消息重新生成”两类，不能重复写入用户消息。
- 小程序切后台或 SSE 中断后，重新进入会话应拉取最终消息状态；生成未完成则展示继续等待或重试。
- 首次 token 前允许自动重试一次；已经输出部分内容后不自动重试，避免重复和费用浪费。

### FR-05 隐私与历史

- “清除全部历史”和“注销账号”提供清晰影响说明。
- 注销账号必须停止处理并删除或匿名化个人数据，法定期限内保留的数据需说明用途。
- 客户端日志不得输出 token、openid、手机号、完整对话内容或模型请求原文。
- 会话默认私密，不生成可被搜索引擎抓取的公开分享链接。

## 7. 技术方案

### 7.1 总体架构

```text
Taro 4 + React / 微信小程序
  -> HTTPS API + SSE（微信端 enableChunked，其他端安全降级）
FastAPI
  -> 认证与用户服务
  -> 会话/消息服务
  -> 内容安全服务
  -> Agent/上下文编排
  -> LLM Provider Adapter
       -> 模型供应商 A
       -> 模型供应商 B
       -> 自有推理服务
PostgreSQL / Redis / 对象存储（P1）
```

FastAPI 是唯一可信后端和模型网关。模型密钥、供应商地址、限流额度、内容安全策略均在服务端配置，禁止通过 `TARO_APP_*` 进入客户端产物。

### 7.2 前端落地建议

- 路由：使用 Taro 文件路由和 `definePageConfig`，不在生成目录中手写路由。
- tabbar：修改 `src/app.config.ts` 与 `src/custom-tab-bar/`，保持“对话”和“我的”两项。
- API：`src/api/` 负责业务操作，`src/service/` 是 OpenAPI 生成物，统一走 `src/services/openapi-request.ts`。
- 流式请求：单独增加 SSE/chunk 适配层，不把普通 JSON 请求包装强行改造成流式。
- 状态：`src/store/chat.ts` 管理当前会话、消息和运行状态；认证继续使用 Zustand。
- 通用聊天组件放在 `src/components/chat/`，页面只订阅 selector 并派发用户意图。
- 长文本和消息列表避免深层响应式包裹；历史消息分页加载，首屏不一次性渲染全部记录。

微信端流式优先方案：

1. `POST` 创建生成任务，持久化用户消息。
2. 使用 `wx.request` 的 `enableChunked` 和 `RequestTask.onChunkReceived` 读取 SSE。
3. 使用增量 UTF-8 解码器，处理中文被拆在多个 chunk 的情况。
4. H5 使用基于 `fetch` 的流式读取；App 或不支持 chunk 的环境降级为轮询任务结果或等待完整响应。
5. 所有 `wx.*` 调用放在 `#ifdef MP-WEIXIN` 中，其他平台提供安全分支。

现有 `src/services/openapi-request.ts` 基于 `Taro.request`，只承载普通 JSON；流式能力由 `src/services/sse/` 独立承载。

### 7.3 FastAPI API 草案

统一前缀：`/api/v1`，错误响应包含 `code`、`message`、`requestId`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/auth/wx-login` | code 登录 |
| POST | `/auth/refresh` | 刷新 token |
| POST | `/auth/logout` | 注销当前会话 |
| GET | `/conversations` | 会话游标分页 |
| POST | `/conversations` | 新建会话 |
| PUT | `/conversations/{id}` | 重命名会话 |
| DELETE | `/conversations/{id}` | 软删除会话 |
| GET | `/conversations/{id}/messages` | 消息游标分页 |
| POST | `/conversations/{id}/messages` | 幂等提交用户消息并创建生成任务 |
| GET | `/runs/{runId}/events` | SSE 订阅生成事件 |
| POST | `/runs/{runId}/cancel` | 停止生成 |
| POST | `/runs/{runId}/retry` | 基于原用户消息重新生成 |
| GET | `/runs/{runId}` | 查询任务最终状态 |

提交消息示例：

```json
{
  "clientMessageId": "uuid-v4",
  "content": {
    "type": "text",
    "text": "帮我整理下面这段内容"
  },
  "stream": true
}
```

返回 `201`：

```json
{
  "userMessage": { "id": "msg_u", "status": "completed" },
  "assistantMessageId": "msg_a",
  "runId": "run_x"
}
```

SSE 事件类型：

- `meta`：模型别名、消息 ID、请求 ID。
- `delta`：新增文本片段。
- `usage`：输入/输出 token 和计费信息，仅内部使用。
- `done`：最终状态和完成时间。
- `error`：稳定错误码，不暴露供应商堆栈。

`GET /runs/{id}/events` 通过 `Authorization` 头鉴权，支持 `Last-Event-ID` 或 `after` 游标重连。SSE 只负责实时体验，最终完整消息必须落库，客户端重连后可查询最终状态。

### 7.4 LLM Provider 抽象

```python
class LLMProvider(Protocol):
    async def stream(
        self,
        messages: list[ChatMessage],
        model: str,
        max_tokens: int,
        timeout_s: float,
    ) -> AsyncIterator[ChatDelta]: ...
```

- 统一模型别名，例如 `default`、`fast`、`reasoning`，避免客户端依赖具体供应商名称。
- 适配 OpenAI-compatible、DashScope、DeepSeek 等服务时只新增 adapter，不修改会话 API。
- 支持超时、取消、熔断、并发上限和供应商故障切换。
- 故障切换只允许发生在首 token 前；已有输出后切换会造成内容不一致，应直接失败并提供重试。
- 记录供应商、模型、延迟、token、错误码和 request ID；默认不记录完整用户内容。

### 7.5 数据模型

| 表 | 关键字段 |
| --- | --- |
| `users` | `id`、`openid`、`unionid`、`nickname`、`avatar_url`、`status`、`created_at` |
| `conversations` | `id`、`user_id`、`title`、`model_alias`、`last_message_at`、`deleted_at` |
| `messages` | `id`、`conversation_id`、`role`、`content_json`、`status`、`client_message_id`、`created_at` |
| `runs` | `id`、`conversation_id`、`user_message_id`、`assistant_message_id`、`provider`、`model`、`status`、`usage_json`、`error_code` |
| `usage_daily` | `user_id`、`date`、`message_count`、`input_tokens`、`output_tokens` |

关键约束：

- `client_message_id` 与 `conversation_id` 建立唯一约束。
- 消息和 run 状态使用固定枚举，避免前后端自由文本判断。
- 所有查询必须带 `user_id` 隔离，禁止只凭会话 ID 访问。
- 软删除后继续访问历史需明确策略；默认对用户立即不可见。

### 7.6 安全、合规与成本

- 上线前完成小程序备案、隐私政策、用户协议、AI 生成内容标识和适用的算法/生成式 AI 合规评估。
- 输入和输出均接入内容安全审核；命中策略时返回统一、可申诉或可重试的提示。
- 输入长度、请求频率、并发数、每日额度和最大输出 token 均由服务端限制。
- 防止提示词注入扩大权限；未来工具调用必须使用允许列表、参数校验和独立超时。
- 小程序端使用合法备案 HTTPS 域名，并在微信公众平台配置 request、socket、uploadFile 合法域名。
- token 仅存本地持久化状态，刷新失败立即清理；后端日志对 token、openid 和消息内容脱敏。
- 对外接口统一限流，按用户、IP 和设备维度组合防护，避免刷模型费用。

## 9. 指标

### 9.1 北极星指标

每周至少完成一次“发送问题并成功收到 AI 回复”的有效用户数。

### 9.2 核心指标

- 首屏可交互时间、首 token 时间 P50/P95、完整回复成功率和中断率。
- 新用户首条消息转化率、次日/7 日留存、平均有效对话轮次。
- 消息失败率、重试成功率、停止生成比例。
- 单有效用户模型成本、token 与缓存命中情况。
- 内容拦截率、用户举报率和限流命中率。

### 9.3 埋点边界

- 只采集行为事件和性能数据，默认不上传完整对话正文。
- 必须记录 `requestId`、`conversationId`、`runId` 的脱敏关联值，便于排障。

## 10. 验收标准

- 新用户可选择同意隐私协议并通过微信 code 登录；拒绝授权有明确降级路径。
- 登录成功后可以新建会话、发送文字、看到流式回复、停止生成、重试失败消息。
- 退出重进后可恢复历史会话；分页、空态、加载态、失败态和重试均可用。
- 断网、接口 401、429、模型超时和流中断均有稳定提示，不出现重复消息。
- 会话和消息有严格用户隔离；删除和清空历史有二次确认。
- 微信开发者工具 Console 无新增报错，Network 无非法域名和 4xx/5xx 阻断。
- 生产构建通过 `pnpm.cmd type-check`、`pnpm.cmd exec eslint src`、`pnpm.cmd test:run` 和 `pnpm.cmd build:mp:prod`。
- 微信模拟器完成登录、四类消息状态、tabbar、安全区和冷启动验收；真机完成授权成功/拒绝和弱网测试。
- 主包低于 2 MB，模型密钥不出现在客户端产物和公开配置中。

## 11. 里程碑
